## Analisis Akar Masalah & Solusi
1. **Windows Protected Directory Permissions**:
   - `C:\Program Files` menolak akses tulis dari proses non-elevated.
   - Solusi: Memperbarui `get_app_dir()` di `backend/config.py` agar mengalihkan penyimpanan data dinamis (`settings.json`, `users.json`, `cookies.txt`, `history.json`) ke `%APPDATA%\StudioDownload`.
   - Melindungi seluruh panggilan slot Qt dialog dalam blok `try...finally:` agar `self.reject()` atau `self.accept()` selalu dieksekusi.
   - Menyimpan flag `"onboarding_completed": True` agar pengguna tidak terkunci dalam perulangan prompt onboarding di setiap startup.
2. **YouTube Playlist Query Collision**:
   - Ketika URL berisi `&list=...`, `yt-dlp` secara default mengekstrak seluruh playlist alih-alih video yang sedang ditonton.
   - Solusi:
     - Mengimplementasikan `normalize_youtube_url(url)` di `backend/parser.py` untuk membersihkan parameter `list`, `index`, `si`, `t`, `feature` ketika ID video `v=` atau `youtu.be/` terdeteksi, menghasilkan URL kanonikal `https://www.youtube.com/watch?v=VIDEO_ID`.
     - Mengaktifkan opsi `'noplaylist': True` pada `ydl_opts` di `parser.py` dan `downloader.py`.
     - Menormalkan URL input di `MainWindow` secara otomatis saat tombol `RUN_ANALYZE` ditekan.
3. **Dokumentasi Keputusan Arsitektural**:
   - Mendokumentasikan solusi lengkap ke dalam [[ADR-009-YouTube-URL-Normalization-and-Installer-Permission-Hardening]].

## Sesi Lanjutan 6: Eliminasi Penurunan Otomatis ke 360p & Akselerasi Pemotongan Segmen Video Durasi Panjang
1. **Permintaan Pengguna**:
   - *"masih 360p"* (File hasil unduhan tetap beresolusi 360p meskipun dipilih 1080p).
2. **Analisis Akar Masalah (Root Cause)**:
   - **Override Client Player**: Di `backend/downloader.py`, injeksi `player_client = ['web', 'mweb', 'android', 'ios']` menyebabkan yt-dlp melewati client android/ios (karena ada cookies) dan client `mweb` mewajibkan GVS PO Token untuk format HTTPS DASH (1080p, 720p). Akibatnya, yt-dlp mengosongkan seluruh stream DASH beresolusi tinggi (`1080p: []`).
   - **Fallback Format 18 (360p)**: Di akhir selektor format terdapat opsi fallback `/best`. Pada YouTube, jika stream terpisah (video+audio) gagal dipilih, `/best` secara default jatuh ke itag 18 (stream tunggal gabungan 640x360).
   - **Soft-Seeking Draining FFmpeg**: Pada video panjang (~5 jam) dengan pemotongan segmen (misal di menit ke-4 jam 27 menit), penggunaan stream fragmented MP4 biasa (`299`/`137`) memaksa demuxer FFmpeg melakukan soft-seeking dengan men-drain data dari byte 0 (menguras 8+ GB data lewat HTTP) sebelum mencapai timestamp target.
3. **Solusi & Implementasi**:
   - **Hapus Override `player_client`**: Menghapus baris injeksi `player_client` di `backend/downloader.py` agar yt-dlp menggunakan default suite (`web`, `tv`, `web_creator`) yang mengekstrak stream 1080p/4K tanpa kendala PO token.
   - **Hapus Fallback `/best`**: Mengganti semua fallback penutup menjadi `/bestvideo+bestaudio` sehingga tidak akan pernah turun ke stream tunggal 360p itag 18.
   - **Optimasi Pemotongan Segmen (HLS Native m3u8)**:
     - Untuk download klip/segmen (`download_ranges`), downloader secara cerdas memprioritaskan stream `m3u8_native` (`protocol^=m3u8`) pada resolusi target (misal `312`/`617` untuk 1080p dan `234` untuk audio).
     - Karena HLS telah terbagi dalam potongan segmen CDN diskrit, FFmpeg langsung mengambil chunk `.ts` pada rentang detik yang diminta (~1 MB) dalam hitungan detik (~5-10 detik untuk klip jam ke-4) tanpa perlu men-drain gigabytes data.
     - Menonaktifkan `force_keyframes_at_cuts` untuk mengaktifkan direct stream copy (`-c copy`) yang cepat dan lossless tanpa degradasi kompresi ulang CPU.
4. **Verifikasi**:
   - Tes end-to-end pemotongan klip jam ke-4 (detik 16020-16025) berhasil 100% dalam 11 detik.
   - Hasil validasi `ffprobe`: `width=1920, height=1080, codec=vp9/h264`, ukuran ~1.34 MB, terbukti 1080p Full HD murni.
